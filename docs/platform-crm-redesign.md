## 1. 目指す運営

クリニックマッチは、運営が売り手と買い手の間に入り、条件確認・提案・合意・契約・引渡しを進める仲介サービスである。管理画面の主役は「公開件数」ではなく「次に進めるための対応」とする。

一つの案件を開けば、次の問いに答えられることを受入基準にする。

- 誰の、どの機器・希望条件についての相談か。
- 売り手・買い手はそれぞれ誰か。運営担当は誰か。
- 最後に誰へ何を伝え、何が確認できたか。
- 次は誰に、何を、いつまでに連絡するか。
- 相手待ちなのか、運営が止めているのか。何が不足しているか。
- 合意・契約・請求・引渡しはどこまで進んだか。

「公開済み」は集客の状態、「対応中」は運営の状態、「交渉中」は商談の状態。それぞれ別に保持する。同じ組織の相談と買いたい投稿は関連候補として見せるが、自動で同じ案件に結合しない。

## 2. あるべき利用者の流れ

| 段階           | 会員側の体験                                                                               | 運営側の仕事・必要情報                                                                         |
| -------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 閲覧・相談     | 未登録でも相談できる。相談には返信先が必要。公開ページへの個人情報掲載とは分ける           | 相談内容、返信先、受付元、関連機器、受付時刻を保存。通知失敗でも受付を失わない                 |
| 会員登録       | 認証、組織、担当者を登録。メール確認と法人確認の状態を区別。途中失敗から再開できる         | 未完了登録と確認待ちを把握。既存組織への参加は招待・確認を経る。法人番号一致だけで加入させない |
| 売りたい       | 機器・状態・保守・付属品・所在・売却額・希望時期を段階入力。下書き→確認→審査提出           | 不足情報を聞き、掲載可否と理由を記録。投稿者と連絡担当を特定                                   |
| 買いたい       | 機種が決まっている／目的から探したいを選択。予算・地域・導入期限・必須条件・代替可否を登録 | 条件の優先順位を確認。候補の有無、提案日、反応、再提案期限を記録                               |

| 候補提案・仲介 | 運営を介した匿名のやり取り。誰からの回答待ちか分かる                                       | 売り手側・買い手側の連絡履歴、希望条件、次回予定を並べる                                       |
| 合意・契約     | 連絡先開示への双方の合意、仲介契約、売買条件を順に確認                                     | 合意の日時・方法・証跡。契約相手と売買当事者の一致を確認                                       |
| 成約・引渡し   | 支払・搬出・搬入・受領・問い合わせ先を確認                                                 | 成約額、売り手への仲介手数料7.5%、契約、請求、引渡し、入金確認を管理                           |
| 見送り・再開   | 理由を残して保留・終了。再開可能                                                           | 失注理由・再接触日。元の相談、投稿、履歴は削除しない                                           |

マイページは「自分の次の作業」「運営の確認待ち」「進行中の取引」を先頭に置く。現時点のマイページ全体はまだこの構成へ刷新していない。

フォームは「連絡先」「条件」「確認・提出」の短い段階にし、公開される項目と運営だけが見る項目を明示する。相談受付と公開投稿を同じ完了文言にしない。「相談を受け付けました」「審査に提出しました」「下書きを保存しました」を使い分ける。

## 3. CRMの画面構成

### 今日の対応

上段に期限超過・本日期限・対応履歴未登録・次回予定なし。下に、期限／運営担当／相手と案件／次の対応／連絡先／対応状態の一覧を置く。メール未送信や取得エラーを0件に見せない。

初期移行時の古いデータは「未対応」と断定せず「対応履歴未登録」とする。電話やメールで既に対応済みの可能性があるため、運営が確認して履歴と次回予定を登録する。

### 案件詳細

左側に顧客・連絡先・元の相談や投稿。右側に次回予定と対応記録。下に時系列の履歴。連絡先には「相談時に指定」「組織」「会員登録メール」の出所を示す。担当者候補が複数いる場合は一人に断定しない。

対応中／返信待ちでは担当・次の対応・期限を必須にする。「返信待ち」でも再確認日が必要。内部メモは連絡実績とは分け、最終連絡日は電話・メール等の記録で更新する。

完成形では、案件詳細に売り手／買い手双方のカード、候補提案、複数タスク、合意、契約、請求、引渡しの進行を統合する。今回の実装は、受付・投稿・アプローチ・スレッドに一つずつ対応管理を付ける第一段階。商談への明示的な関連付けと双方別タスクは次段階とする。

### 状態とデータの境界

| 対象       | 状態例                                               | 保持する事実                           |
| ---------- | ---------------------------------------------------- | -------------------------------------- |
| 受付・投稿 | 新規、下書き、審査中、差し戻し、公開                 | 提出内容・投稿者・審査結果             |
| 対応ケース | 未整理、対応中、返信待ち、保留、完了                 | 運営担当・次の対応・期限・最終連絡     |
| 対応履歴   | 電話、メール、LINE、面談、内部メモ                   | 実施者・相手・日時・結果。上書きしない |
| 商談       | 候補提案、条件確認、交渉、契約、引渡し、成約、見送り | 双方・関連投稿・条件・証跡             |
| 通知       | 未送信、送信処理中、送信成功、失敗                   | 受付そのものの成功とは別管理           |

## 4. 調査で確認した問題

前回の本番読み取り時点：売りたい27件、買いたい4件、相談8件。相談8件は全てnewだが、テストと実際の問い合わせが混在。件数だけでは実対応状況を判断できない。アプローチ・スレッド・メッセージは0件だった。

9月8日の買いたい投稿と購入相談はDBに存在した。相談の連絡先欄が空でも、組織・会員・Authのメールを辿れるケースがある。一方、8月22日の相談には直接連絡先も組織との紐付けもなく、DBだけでは返信先を特定できなかった。既存データに推測で連絡先を補完していない。

## 5. 今回の実装

- `/admin` を「今日の対応」にし、`/admin/crm` と案件詳細を追加。受付・投稿・アプローチ・スレッドを横断する。既存管理ページからもCRMへリンクする。
- CRM状態、担当、次の対応、JSTの期限、相手、記録、実施日時を保存。同時編集は409で止め、再送は重複記録にしない。
- 旧相談フォームを保存付きの共通受付に変更。通知失敗時も相談を残し、管理詳細で通知を再試行できる。相談通知には個人情報を本文に載せず管理詳細へ誘導する。
- 会員登録はAuthとプロフィールの状態を確認して再開。一般会員の役割・組織・法人確認等の直接変更を制限する。
- 投稿の審査状態と編集可能状態を制限。差し戻し理由を保存し、会員側で表示。保管と復元を追加する。
- 仲介開始・連絡先開示を原子的なDB処理へ移し、合意証跡を追加する。

追加SQLは `0011_intake_crm.sql`〜`0017_comment_trigger_compatibility.sql`。既存テーブルの削除・既存行の一括更新・既存マイグレーションの書き換えは行っていない。ただし新しい権限制御は今後の書き込み動作を変えるため、ステージングで既存フローを検証してから適用する。

## 6. 次の実装範囲と残る制約

1. **会員・投稿UXの刷新**：段階入力、公開／非公開項目の明示、未完了登録と審査待ちのマイページ表示、登録確認メールの実環境試験。組織参加の招待フローは未実装。
2. **投稿保存と画像の耐障害性**：追加改修で作成再送キー、画像操作の原子性、保管・復元、旧ファイル保持を実装。残るのは実Supabase Storageとの結合試験、未参照ファイルの運用、タブを閉じた後の入力再開。詳細は続編に記載。
3. **商談単位のCRM**：相談・投稿の明示的な紐付け、候補提案、売り手／買い手別の複数タスク、契約・請求・引渡し期限を統合する。現在は案件あたり次の対応を一つ保持し、双方の連絡は既存ワークスペースと履歴の相手欄を使う。
4. **通知の確実性**：受付通知は保存状態と手動再試行まで。全通知のoutbox、遅延処理、自動再試行、利用者への受付確認メールは未整備。今回の共通相談受付は管理者通知のみで、旧一般相談の自動返信メールは送らない。画面の受付完了を基準とし、利用者向けメールは専用の再送管理を設けて復帰する。
5. **運用監視**：担当未割当、通知失敗、連絡先不足、放置、契約／請求未完了を抽出。無断の自動連絡はしない。初回対応は翌営業日、返信待ちの再確認は3営業日を提案値とする（未設定・業務側で調整）。
6. **データ量と検索**：現実装は各テーブル最大5000件、画面50件単位。上限・取得失敗は警告する。拡大前にDB側検索・集計へ移す。会員Authメールは詳細のみ取得するため一覧検索対象にはならない。履歴は最新100件表示。
7. **既存画面の追加監査**：公開コメント・画像・通知テンプレート全体の匿名性、メッセージ編集、契約・請求の全状態遷移は追加試験が必要。今回の修正だけで全経路の安全性を保証しない。

## 7. 既存DBを壊さない導入手順

1. 読み取り専用で本番のスキーマ、マイグレーション履歴、制約、RLS、権限、件数、孤立参照を再取得する。リポジトリSQLとの相違を確認する。ローカル試験は既存マイグレーションと確認済みの本番固有ポリシーを再現済み。ただしAuth・Storageは代替定義であり、本番の完全な複製ではない。
2. バックアップと復元先を確認し、復元可能なステージングへ複製する。実メール送信を無効にしてテストする。
3. ステージングで追加SQLを順番に適用し、既存レコードの旧列値が保持されることを比較する。各SQLはトランザクションと5秒のロック待ち制限を持つ。失敗を無視して次へ進めない。
4. 既存会員ログイン、新規登録・途中再開、売りたい／買いたいの下書き・画像・審査・差し戻し・再提出、問い合わせ、仲介開始・開示・契約・成約を検証する。匿名ユーザー・別組織・一般会員・管理者で権限確認する。
5. SQLとアプリを同じ切替計画で導入する。旧アプリのプロフィール作成や直接相談INSERT等は新制御で止まるため、無計画にSQLだけ先行させない。切替中の書き込み停止時間を決める。
6. 本番適用後は既存相談を勝手に移行・統合・連絡済みにしない。運営が原本メール等を確認し、CRMに担当と次回予定を入れる。関連が不明なものは未確認として残す。
7. 不具合時は新データを消さず書き込みを止めて診断する。安易なテーブルDROPやmigration reset、旧アプリのみへの巻き戻しは行わない。新制御を考慮した互換修正を行う。
